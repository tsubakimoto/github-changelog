## Copilot Memory has more controls for deletion, scope, and the Copilot CLI

**URL:** https://github.blog/changelog/2026-05-26-copilot-memory-has-more-controls-for-deletion-scope-and-the-copilot-cli

### 要約
Copilot Memory に、削除の案内改善、リポジトリ単位のオフ切り替え、そして Copilot CLI からの操作が追加されました。`/memory on`、`/memory off`、`/memory show` でセッションをまたいだ制御ができ、保存時のスコープもより明確になります。

### ユーザーにとって良いこと
- メモリの有効/無効や状態確認を CLI から直接行えます
- リポジトリ単位で Copilot Memory を止められるため、管理ポリシーに合わせやすくなります
- 保存時にユーザー設定かリポジトリ情報かが明示され、意図しない保存を避けやすくなります

### アクションプラン
- **Copilot CLI を使うチーム**: `/memory show` で現在の状態を確認し、必要なら `/memory off` を運用手順に追加してください
- **リポジトリ管理者**: Repository Settings > Copilot > Memory で、対象リポジトリの保存可否を見直してください
- ⚠️ **注意**: リポジトリ側のオフ設定は既存の facts を削除しません。削除が必要なら別途メモリ管理画面で対応してください

### リファレンス
- [Copilot Memory has more controls for deletion, scope, and the Copilot CLI](https://github.blog/changelog/2026-05-26-copilot-memory-has-more-controls-for-deletion-scope-and-the-copilot-cli)

## GitHub Code Quality: Repository Enablement API

**URL:** https://github.blog/changelog/2026-05-26-github-code-quality-repository-enablement-api

### 要約
GitHub Code Quality をリポジトリ単位で有効化・設定できる Repository Enablement API が public preview で提供されました。`PATCH /repos/{owner}/{repo}/code-quality/setup` と `GET /repos/{owner}/{repo}/code-quality/setup` で、言語、runner、分析スケジュールなどを操作できます。

### ユーザーにとって良いこと
- リポジトリの Code Quality 設定を API から自動化できます
- 複数リポジトリの初期設定や標準化をスクリプト化しやすくなります
- 対象言語が明示されているため、導入範囲を判断しやすくなります

### アクションプラン
- **プラットフォーム管理者**: 既存のプロビジョニング処理に Code Quality 設定 API を組み込んでください
- **CI/自動化担当**: リポジトリ作成フローで `PATCH` を呼び出し、標準設定を適用してください
- ⚠️ **注意**: この機能は github.com の public preview で、Enterprise Server では利用できません

### リファレンス
- [GitHub Code Quality: Repository Enablement API](https://github.blog/changelog/2026-05-26-github-code-quality-repository-enablement-api)

## Target Copilot models to organizations with model rules

**URL:** https://github.blog/changelog/2026-05-26-target-copilot-models-to-organizations-with-model-rules

### 要約
Enterprise owners が、組織ごとに利用可能な Copilot モデルを細かく指定できる model rules が public preview になりました。あわせて、デフォルトモデルの可用性管理画面も刷新され、Enabled / Optional の切り替えがしやすくなっています。

### ユーザーにとって良いこと
- 組織ごとにモデルを制御でき、用途や部門ごとの最適化がしやすくなります
- 企業全体の一律設定よりも柔軟に、段階的な展開や制限ができます
- 管理画面が整理され、どのモデルがどの組織で有効かを把握しやすくなります

### アクションプラン
- **Enterprise owner**: まずは少数の組織で rule を作り、意図どおりのモデルが出るか確認してください
- **運用担当**: デフォルトの Enabled / Optional 方針を整理し、組織ごとの例外ルールを文書化してください
- ⚠️ **注意**: Copilot Business / Enterprise 契約が前提です。組織の権限設計と併せて見直してください

## Dependabot version updates now support the sbt ecosystem

**URL:** https://github.blog/changelog/2026-05-26-dependabot-version-updates-now-support-the-sbt-ecosystem

### 要約
Dependabot が sbt を version updates の対象エコシステムとしてサポートしました。`.github/dependabot.yml` に sbt を追加すると、`build.sbt` の入力を監視して upstream の新しい commit を元に PR を作成します。

### ユーザーにとって良いこと
- Scala / sbt プロジェクトでも Dependabot による更新追従を自動化できます
- 依存更新の見落としを減らし、保守負荷を下げられます
- セキュリティ更新ではなく version updates に限定されるため、期待する動作を整理しやすいです

### アクションプラン
- **sbt を使うリポジトリ**: `.github/dependabot.yml` に sbt エントリを追加してください
- **保守担当**: 次回の Dependabot 実行後に、更新 PR が想定どおり出るか確認してください
- **注意**: これは version updates のみです。security updates を期待する設定にはしないでください

### リファレンス
- [Dependabot version updates now support the sbt ecosystem](https://github.blog/changelog/2026-05-26-dependabot-version-updates-now-support-the-sbt-ecosystem)

## Filter secret scanning approval requests by sort order and bypass status

**URL:** https://github.blog/changelog/2026-05-26-filter-secret-scanning-approval-requests-by-sort-order-and-bypass-status

### 要約
Secret scanning の承認・却下フローに、UI での並び替えと REST API の `is_bypassed` フィルターが追加されました。これにより、大規模な組織でも bypass や dismissal のリクエストをより扱いやすくなります。

### ユーザーにとって良いこと
- UI で新しい順 / 古い順 / 更新順を選べるため、処理優先度をつけやすくなります
- API でも bypass 状態で絞り込めるので、自動処理やレポート作成が簡単になります
- リポジトリ、organization、enterprise の各レベルで同じ考え方で運用できます

### アクションプラン
- **セキュリティ運用担当**: UI の並び順を見直し、期限が近いリクエストを先に処理してください
- **API 利用者**: `is_bypassed=true/false` を使って alert の取得ロジックを更新してください
- **自動化担当**: 既存の一覧処理に bypass 条件を追加し、後処理の分岐を整理してください

### リファレンス
- [Filter secret scanning approval requests by sort order and bypass status](https://github.blog/changelog/2026-05-26-filter-secret-scanning-approval-requests-by-sort-order-and-bypass-status)

## GitHub Classroom sign-ups are no longer available

**URL:** https://github.blog/changelog/2026-05-26-github-classroom-sign-ups-are-no-longer-available

### 要約
GitHub Classroom の新規 sign-up が停止され、既存ユーザーは引き続き利用できますが、2026-08-28 に partner solutions への完全移行が予定されています。GitHub ユーザーアカウント、リポジトリ、organization への影響はありません。

### ユーザーにとって良いこと
- 既存の classroom は当面そのまま使い続けられます
- 影響範囲が明確で、移行対象と非対象を区別しやすくなります
- 教育用途の代替先を検討するための猶予期間が示されています

### アクションプラン
- **既存の Classroom 管理者**: 2026-08-28 までに partner solutions への移行計画を立ててください
- **新規導入を検討していた教育機関**: 代替サービスの比較と移行手順の確認を進めてください
- ⚠️ **注意**: 2026-08-28 以降は classroom の管理にサインインできなくなります

## Code coverage on pull requests is now in public preview

**URL:** https://github.blog/changelog/2026-05-26-code-coverage-in-pull-requests-is-now-in-public-preview

### 要約
GitHub Code Quality のユーザー向けに、Pull Request 上で aggregate code coverage を表示できる機能が public preview になりました。既存の CI から Cobertura レポートをアップロードすると、レビュー時にテスト充足度の目安を直接確認できます。

### ユーザーにとって良いこと
- PR 上で coverage が見えるため、レビュー判断が速くなります
- 追加の外部ツールに切り替えずに、品質シグナルを確認できます
- 既存 CI を活かしたまま導入でき、移行コストを抑えられます

### アクションプラン
- **Code Quality 利用者**: リポジトリで code coverage を有効化してください
- **CI 担当**: `upload-code-coverage` action で Cobertura レポートを送信するステップを追加してください
- ⚠️ **注意**: GitHub Apps と Actions workflow には `code-quality:write` 権限が必要です。Enterprise Server は未対応です

### リファレンス
- [Code coverage on pull requests is now in public preview](https://github.blog/changelog/2026-05-26-code-coverage-in-pull-requests-is-now-in-public-preview)
