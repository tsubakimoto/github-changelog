## Rate limits for private vulnerability reports

**URL:** https://github.blog/changelog/2026-10-01-rate-limits-for-private-vulnerability-reports

### 要約
Private vulnerability reporting に、1アカウントが1日に送信できる新規レポート数の制限が導入されました。リポジトリ管理者はリポジトリ全体の1日あたりの上限を設定でき、信頼できる報告者を許可リストに登録して制限対象外にできます。

### ユーザーにとって良いこと
大量または自動生成された低品質な報告がセキュリティ対応を埋もれさせることを防ぎ、重要な脆弱性を見つけやすくなります。既存アドバイザリへのコメントは制限されないため、進行中の調査や対話は継続できます。

### アクションプラン
- Private vulnerability reporting を有効にしている公開リポジトリで、Settings > Advanced Security > Private vulnerability reporting の上限と許可リストを確認する。
- セキュリティ研究者からの正当な報告を確実に受け付けるため、信頼できる報告者を許可リストへ追加する。
- リポジトリ単位の上限を設定する場合は、通常の報告量とインシデント時の余裕を考慮して値を決める。
- GitHub Free、Pro、Team、Enterprise Cloud の対象公開リポジトリに自動適用されるため、不要な設定変更はない。

## Structured forms for private vulnerability reports

**URL:** https://github.blog/changelog/2026-10-01-structured-forms-for-private-vulnerability-reports

### 要約
Private vulnerability reporting の報告フォームが構造化され、概要、詳細、150文字以上の再現可能なProof of Concept、影響の4項目を標準で求めるようになりました。リポジトリの `.github/VULNERABILITY_REPORT.yml`、または組織・アカウントの `.github` リポジトリでフォームをカスタマイズでき、CWEの必須化やAI利用の申告にも対応します。

### ユーザーにとって良いこと
報告に必要な情報が揃いやすくなり、メンテナーは脆弱性の再現性や影響を短時間で評価できます。報告者にとっても、何を記載すべきかが明確になり、API連携ではリポジトリが要求するフォームを確認して互換性を保てます。

### アクションプラン
- Private vulnerability reporting を利用するリポジトリで、標準フォームが運用に適しているか確認する。
- 追加情報や最小文字数が必要な場合は、デフォルトブランチの `.github/VULNERABILITY_REPORT.yml` を作成し、組織共通にする場合は組織・アカウントの `.github` リポジトリへ配置する。
- REST APIで報告を送信する既存連携は、カスタムフォームの必須項目と新しいフォーム取得エンドポイントに対応する。
- 組織・エンタープライズ管理者は、CWE必須化や `SECURITY.md` の導線を含む運用ポリシーを確認する。
- GitHub Free、Pro、Team、Enterprise Cloud の対象公開リポジトリに提供され、カスタムフォームが無効な場合はデフォルトフォームへフォールバックする。

## GitHub Copilot can now interact with desktop apps with computer use

**URL:** https://github.blog/changelog/2026-10-01-github-copilot-can-now-interact-with-desktop-apps

### 要約
GitHub Copilot CLI と macOS／Windows版 GitHub Copilot アプリで、デスクトップアプリを操作できるComputer Useがパブリックプレビューになりました。Copilotは画面やアクセシビリティ情報を読み取り、クリック、入力、スクロールなどを実行できますが、操作前に承認を求め、組織設定で無効化することもできます。

### ユーザーにとって良いこと
API、CLI、MCP連携を持たないレガシーソフトやGUI専用ツールを含む業務フローも自動化できます。ユーザー承認、常時許可アプリの確認・リセット、macOSの権限案内により、操作の制御権を保てます。

### アクションプラン
- Copilot CLIで試す場合は `/computer on`、状態確認は `/computer show`、停止は `/computer off` を使う。
- macOSではAccessibilityとScreen Recordingの権限を確認し、組織利用では管理設定で許可されているか確認する。
- 自動操作を依頼する際は、達成したい結果、対象アプリ、重要な制約を具体的に記述し、承認内容を確認してから実行する。
- パブリックプレビュー機能のため、本番の重要操作では実行結果を必ず確認し、不要時は無効化する。

## GitHub Actions: macOS 14 runner image retirement

**URL:** https://github.blog/changelog/2026-10-01-github-actions-macos-14-runner-image-retirement

### 要約
macOS 14のGitHub Actionsランナーイメージは2026年11月2日に廃止されます。廃止前には2026年10月5日から10月31日にかけて複数のブラウンアウトが実施され、`macos-14`、`macos-14-large`、`macos-14-xlarge` を使うジョブが一時的に失敗します。

### ユーザーにとって良いこと
早期に新しいランナーへ移行することで、廃止後のCI停止やブラウンアウト中の失敗を回避できます。macOS 15またはmacOS 26系のラベルへ移行することで、サポートされるツールチェーンを利用できます。

### アクションプラン
- ワークフロー内の `runs-on` を検索し、`macos-14`、`macos-14-large`、`macos-14-xlarge` の利用箇所を洗い出す。
- 2026年11月2日までに `macos-15`、`macos-15-xlarge`、`macos-latest`（macOS 26）、`macos-latest-xlarge` のいずれかへ更新し、ビルド・署名・テストを検証する。
- 2026年10月5日以降のブラウンアウト日程をリリース計画に反映し、移行完了までのCI失敗を想定する。
- ⚠️ 2026年11月2日以降、macOS 14ラベルは廃止されるため、対象ワークフローを必ず移行する。

- [GitHub Actions: macOS 14 runner image retirement](https://github.blog/changelog/2026-10-01-github-actions-macos-14-runner-image-retirement)

## Actions retention now covers checks, runs, and statuses

**URL:** https://github.blog/changelog/2026-10-01-actions-retention-now-covers-checks-runs-and-statuses

### 要約
GitHub Actionsの保持期間設定が、アーティファクトとログだけでなく、チェック、ワークフロー実行、ステータスにも適用されるようになりました。設定期間を超えたこれらの記録は、エンタープライズ、組織、リポジトリの設定に従って自動削除されます。

### ユーザーにとって良いこと
CI関連データの保持を一つのポリシーで管理でき、不要な履歴による保存コストや情報残存を抑えられます。GitHub Actionsとサードパーティアプリが作成したチェックやステータスも同じ基準で整理されます。

### アクションプラン
- リポジトリの「Check, workflow run, status, artifact and log retention」設定を確認し、監査・デバッグ要件に合う保持期間へ更新する。
- 重要な実行結果や監査記録を保持する必要がある場合は、期限前に外部保存などの運用を準備する。
- ⚠️ 保持期間を変更しても、すでに削除されたデータは復元されないため、設定変更前に必要な記録を退避する。
- 組織・エンタープライズの上限に従い、公開リポジトリの最大保持期間は90日であることを確認する。

- [Actions retention now covers checks, runs, and statuses](https://github.blog/changelog/2026-10-01-actions-retention-now-covers-checks-runs-and-statuses)

## Scheduled code scanning skips inactive repositories

**URL:** https://github.blog/changelog/2026-10-01-scheduled-code-scanning-skips-inactive-repositories

### 要約
Code scanningのdefault setupとGitHub Code Qualityの週次スキャンは、初回検証スキャンや言語検出変更ではなく、pushまたはpull requestによる分析があった後に開始されるようになりました。これにより、まとめて設定を展開した休眠リポジトリで予期せず週次スキャンが続くことを防ぎます。

### ユーザーにとって良いこと
実際に開発活動があるリポジトリを中心にスキャンされるため、不要な実行やノイズを減らせます。default setupの有効化時に findings をすぐ取得する動作は維持され、設定変更なしでスキャンの挙動が予測しやすくなります。

### アクションプラン
- 既存のdefault setupとCode Qualityの設定変更は不要だが、週次スキャンの開始条件をチームの運用資料へ反映する。
- 大規模展開時は、初回検証スキャンが週次スキャンの活動実績として扱われないことを前提に監視する。
- 休眠リポジトリの検出が必要な場合は、push／pull requestに依存しない別の棚卸し・通知手段を用意する。
- GitHub Enterprise Cloudでは自動適用され、GitHub Enterprise Server 3.24でも対応予定である。

- [Scheduled code scanning skips inactive repositories](https://github.blog/changelog/2026-10-01-scheduled-code-scanning-skips-inactive-repositories)

## Code coverage uploads no longer fail CI for new branches

**URL:** https://github.blog/changelog/2026-10-01-code-coverage-uploads-no-longer-fail-ci-for-new-branches

### 要約
GitHub Code Qualityの`upload-code-coverage`アクションは、まだプルリクエストがない新規ブランチへのpushでは、カバレッジをアップロードせずに成功するようになりました。Actionsのnoticeとstep summaryで理由が示され、デフォルトブランチや対応するプルリクエストイベントのアップロード動作は従来どおりです。

### ユーザーにとって良いこと
プルリクエスト番号がまだ存在しないという正常な状態で、カバレッジ処理がCI全体を失敗させることがなくなります。既存ワークフローを変更せずに新規ブランチの開発を進められます。

### アクションプラン
- 既存のカバレッジアップロード設定は原則変更不要で、空振り時のActions noticeとstep summaryを確認できるようにする。
- PR作成直後にもアップロードしたい場合は、ワークフローに `pull_request` トリガーを追加する。
- pushイベントだけの構成では、PRを開いただけでは再アップロードされないため、次のpushで再実行される運用を周知する。
- GitHub Enterprise CloudとGitHub Teamに提供され、GitHub Enterprise Serverでは利用できない点を環境ごとに確認する。

## Dynamic workflows in Copilot CLI and the Copilot app

**URL:** https://github.blog/changelog/2026-10-01-dynamic-workflows-in-copilot-cli-and-the-copilot-app

### 要約
Copilot CLI、GitHub Copilotアプリ、Copilot SDKで、複数エージェントを含む処理の手順をコードとして定義するDynamic workflowsが利用可能になりました。ステップの直列・並列実行、構造化結果の受け渡し、相互検証、ユーザー入力、チェックポイントでの一時停止と再開に対応します。

### ユーザーにとって良いこと
リリースチェック、障害調査、大規模コードレビューなど、繰り返し実行する複雑な作業を信頼性と可観測性を保ちながら標準化できます。単純な依頼は通常のチャット、明確な段階や制限が必要な処理はDynamic workflowという使い分けが可能です。

### アクションプラン
- 繰り返し実行するリリース確認、障害調査、レビュー、コードベース横断チェックからワークフロー化の候補を選ぶ。
- Copilot CLIでは `--experimental` または対話中の `/experimental on` で実験機能を有効にし、最新バージョンへ更新する。
- 各ステップの入力・出力、並列実行の境界、検証条件、ユーザー確認ポイントをコードで明示する。
- パブリックプレビューで仕様変更の可能性があるため、重要な処理ではチェックポイントと人手レビューを残す。

### リファレンス
- [Dynamic workflows in Copilot CLI and the Copilot app](https://github.blog/changelog/2026-10-01-dynamic-workflows-in-copilot-cli-and-the-copilot-app)
