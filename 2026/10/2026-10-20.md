## Bulk migrate branch protections to rulesets for a repository

**URL:** https://github.blog/changelog/2026-10-20-bulk-migrate-branch-protections-to-rulesets-for-a-repository

### 要約
リポジトリ内のすべてのブランチ保護ルールを、一括でルールセットに変換できるようになりました。変換前に作成されるルールセットや既存ルールセットとの重複を確認し、適用状態を選んだうえで、元のルールを残すか削除するか指定できます。

### ユーザーにとって良いこと
個別に移行する手間を減らしながら、複数ブランチへのパターン適用や階層的なポリシー管理など、ルールセットの機能を活用できます。

### アクションプラン
- 移行する場合はリポジトリの Settings → Rulesets からインポートを開始し、作成内容、既存ルールとの重複、適用状態を確認してから実行してください。この機能はルールセットが利用可能なリポジトリで使えます。
- 変換後に元のブランチ保護ルールを削除するか、既存の挙動と照合してから選択してください。移行は管理者が明示的に実行する操作です。

## Updates to GitHub secret scanning

**URL:** https://github.blog/changelog/2026-10-20-updates-to-github-secret-scanning

### 要約
2026年11月12日以降、対象となる監査ログイベントの `business` フィールドは、エンタープライズの表示名ではなく slug を返すようになります。また、カスタムパターンのアラート状態、Base64 エンコードされたトークンの失効、dismissal-request webhook の番号などが改善され、バイパス関連 API の不具合修正とカスタムパターン API の入力エラーを示す HTTP 422 応答が含まれます。

### ユーザーにとって良いこと
シークレット検出後のアラートや連携の扱いがより安定し、エンコードされたトークンも失効対象にできます。監査ログ連携を更新しておけば、フィールド変更後の処理停止を防げます。

### アクションプラン
- `secret_scanning_alert.*` および `secret_scanning_push_protection.bypass` の監査ログを処理する連携が `business` の表示名で絞り込んでいる場合は、2026年11月12日までに slug も受け入れるよう更新するか、`business_id` を利用してください。
- dismissal-request webhook を処理する場合は、リポジトリと `exemption_request.number` を組み合わせて要求を識別してください。
- カスタムパターン API の連携では、無効な引数に対する `422` を入力エラーとして扱い、サーバーエラーの `500` と区別してください。これらの変更に対して追加の有効化操作は不要です。

## Dependabot alerts REST API now includes dependency versions

**URL:** https://github.blog/changelog/2026-10-20-dependabot-alerts-rest-api-now-includes-dependency-versions

### 要約
Dependabot アラートの REST API 応答に、依存関係の記録済みバージョンまたはバージョン制約を示す `dependency.version_requirement` が追加されました。個別・一覧のアラート応答と `dependabot_alert` webhook で利用でき、値が不明な場合は `null` になります。複数の脆弱なバージョンがある場合にすべてを表すとは限らず、長い制約値は切り詰められることがあります。

### ユーザーにとって良いこと
アラートの同期先で脆弱な依存関係のバージョン情報を使う際、lockfile の解析や GraphQL の追加問い合わせが不要になります。

### アクションプラン
- Dependabot アラートを取り込む連携では `version_requirement` を利用し、`null` や不完全な場合がある値として処理してください。脆弱な全バージョンを示す情報としては扱わないでください。
- REST API の個別・一覧応答と `dependabot_alert` webhook のどちらから情報を取得するか、既存の同期処理に合わせて確認してください。github.com と GitHub Enterprise Cloud with data residency では利用可能で、GitHub Enterprise Server 3.24 に含まれる予定です。

## GitHub package firewall in public preview

**URL:** https://github.blog/changelog/2026-10-20-github-package-firewall-in-public-preview

### 要約
GitHub package firewall がパブリックプレビューとして提供され、パッケージ取得時にメタデータとダウンロードを検査して、マルウェアなどのリスクを評価できるようになりました。管理者がクールダウン期間、GitHub Advisory Database のアラート、サプライチェーンチェックなどのポリシーを設定し、Actions runner や coding agent などの利用先を firewall 経由に構成します。現時点で npm のみをサポートし、GitHub Enterprise Cloud（データレジデンシーを含む）が対象です。

### ユーザーにとって良いこと
パッケージのインストール時にリスクのある依存関係を検出・ブロックし、CI/CD 環境や開発端末の認証情報を狙う攻撃への防御を強化できます。

### アクションプラン
- 対象となる Enterprise Cloud の管理者は、プレビュー利用時にポリシーを設定し、runner や coding agent が upstream registry ではなく firewall を使うよう構成してください。利用には管理者設定とエンドポイント側の設定が必要です。
- npm のみが現時点の対応対象であることを踏まえて対象ワークフローを選び、プレビュー期間中は無料ですが、一般提供後は従量課金となる予定である点も考慮してください。

### リファレンス
- [GitHub package firewall in public preview](https://github.blog/changelog/2026-10-20-github-package-firewall-in-public-preview)

## Dependabot now supports npm 12, pnpm 11 and 12, and Bun 1.4

**URL:** https://github.blog/changelog/2026-10-20-dependabot-now-supports-npm-12-pnpm-11-and-12-and-bun-1-4

### 要約
Dependabot が npm 12、pnpm 11 と 12、および Bun 1.4 に対応し、これらのバージョンを使うプロジェクトでも更新を受け取れるようになりました。github.com の全ユーザーが利用でき、GitHub Enterprise Server 3.24 にも含まれる予定です。

### ユーザーにとって良いこと
新しいパッケージマネージャーのバージョンへ移行した後も、Dependabot による依存関係更新を継続できます。

### アクションプラン
- npm、pnpm、または Bun を該当バージョンへ更新するプロジェクトでは、Dependabot の更新設定を確認し、引き続き更新が作成されることを確認してください。追加の有効化操作は不要です。
- GitHub Enterprise Server を利用している場合は、Dependabot 対応がバージョン 3.24 に含まれる予定であることを踏まえてアップグレード計画を確認してください。
