## Copilot code review: An improved review experience

**URL:** https://github.blog/changelog/2026-09-18-copilot-code-review-an-improved-review-experience

### 要約
Copilot code review のレビュー体験が改善され、レビューの進捗がより分かりやすくなりました。指摘は Open / Resolved since last review / Previously missed に整理され、コメントタイトルも付くようになりました。あわせて、対処済みコメントの自動解決が賢くなり、適格な suggestion をまとめて適用したときにはコミットメッセージも生成されます。

### ユーザーにとって良いこと
どの指摘が残っていて、どれが解消済みかをすぐ把握できるため、レビューの往復が減ります。まとめて修正したあとも履歴が追いやすく、コミット整理までスムーズになります。

### アクションプラン
- Copilot code review を使っているリポジトリでは、レビュー結果の Overview コメントを確認し、Open / Resolved / Previously missed の区分で対応優先度を付ける。
- 既存のレビューフローで Copilot の指摘を手動管理している場合は、コメントタイトルと自動解決の挙動を前提に運用を見直す。
- 自動適用の変更であり、利用側の設定変更は不要。

## Manage the code coverage ruleset condition with the REST API

**URL:** https://github.blog/changelog/2026-09-18-manage-the-code-coverage-ruleset-condition-with-the-rest-api

### 要約
リポジトリルールセットの「Restrict code coverage」を REST API から管理できるようになりました。最小カバレッジや許容される低下幅を、UI だけでなく API 経由で作成・更新・参照できます。GitHub Code Quality と coverage upload の構成が前提で、GHEC と GitHub Team で利用可能です。

### ユーザーにとって良いこと
複数リポジトリにまたがるコードカバレッジ要件を、手作業ではなく自動化で統一できます。IaC や運用スクリプトに組み込めるため、設定漏れやばらつきを減らせます。

### アクションプラン
- リポジトリ群で code coverage ルールを運用しているなら、既存の ruleset 管理手段を REST API ベースに移行する。
- GitHub Code Quality と coverage upload が未設定のリポジトリでは、先に前提条件を満たす。
- これは API の追加機能であり、既存設定は自動変更されないため、導入は任意。

## Upcoming deprecation of selected GitHub Copilot models in mid-October

**URL:** https://github.blog/changelog/2026-09-18-upcoming-deprecation-of-selected-github-copilot-models-in-mid-october

### 要約
Copilot の一部モデルが 2026-10-19 に廃止される予定です。対象は Gemini 3.7 Flash、GPT-5.4 / 5.4 mini / 5 mini、Grok 4.5 で、それぞれ後継候補が案内されています。Copilot の複数体験で共通に影響し、既存ワークフローや統合の更新が必要です。

### ユーザーにとって良いこと
サポート対象モデルが整理され、今後の機能提供や品質改善を後継モデルへ集約しやすくなります。早めに切り替えることで、廃止日当日の動作変化や運用停止を避けられます。

### アクションプラン
- Copilot Chat、inline edits、ask / agent モード、code completions で廃止対象モデルを使っていないか確認する。
- ワークフローや自動化で対象モデルを指定している場合は、案内された代替モデルへ更新する。
- Copilot Enterprise / Business の管理者は、必要に応じてモデルポリシーで代替モデルを有効化する。
- ⚠️ 2026-10-19 以降、対象モデルは利用できなくなるため、期限前に移行を完了する。

## Stage-only npm tokens for safer automation

**URL:** https://github.blog/changelog/2026-09-18-stage-only-npm-tokens-for-safer-automation

### 要約
npm の granular access token に「Read and write (stage only)」が追加され、直接 publish せずに staged release を行えるようになりました。ワークフローは `npm stage publish` でバージョンを提出し、保守者が 2FA 付きで承認して公開します。これは opt-in で、既存トークンの挙動は変わりません。

### ユーザーにとって良いこと
自動化に publish 権限を持たせたまま直接公開させない構成にできるため、誤公開のリスクを減らせます。今後の direct publishing 廃止に向けた移行先としても使えます。

### アクションプラン
- npm publish を使う既存 CI がある場合は、stage-only token と `npm stage publish` への切り替え可否を検討する。
- package maintainer の承認フローと 2FA 要件を運用に組み込む。
- Node.js 22.14.0 以上、npm CLI 11.15.0 以上の前提条件を満たす。
- ⚠️ 2027 年 1 月に向けて direct publish の廃止予定があるため、移行計画を前倒しで進める。
