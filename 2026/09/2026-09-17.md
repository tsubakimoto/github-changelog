## Copilot impact dashboard now shows feature engagement

**URL:** https://github.blog/changelog/2026-09-17-copilot-impact-dashboard-now-shows-feature-engagement

### 要約
Copilot の impact dashboard と usage metrics API に、主要機能ごとの feature engagement が追加されました。Enterprise / organization の 28 日集計で、どの機能が日常利用されているかを把握しやすくなり、AI adoption phase の集計も改善されています。利用状況を「使っている人数」だけでなく「どの機能が定着しているか」まで見られる更新です。

### ユーザーにとって良いこと
チームがどの Copilot 機能を実際に使っているかを可視化でき、導入効果の高い領域と追加の支援が必要な領域を見分けやすくなります。管理者は、教育や設定変更を感覚ではなく実データに基づいて進められます。

### アクションプラン
- Copilot usage metrics policy を有効にしたうえで、enterprise / organization の 28 日レポートに `copilot_feature_engagement` が出るか確認してください。
- `totals_by_feature` と `users_in_phase_28d` を使い、コード補完・CLI・cloud agent などの利用傾向を定例レポートに組み込んでください。
- 機能ごとの利用が偏っている場合は、低利用機能に対するオンボーディングや設定見直しを実施してください。

## Agentic CLI customizations now in the usage metrics API

**URL:** https://github.blog/changelog/2026-09-17-agentic-cli-customizations-now-in-the-usage-metrics-api

### 要約
Copilot CLI の usage metrics API に、skills、custom agents、MCP servers、slash commands、plugins の利用状況が追加されました。1 日 / 28 日の per-user と aggregate レポートで、何がよく使われているか、どれだけ種類が広がっているかを確認できます。CLI の自動化や拡張の定着度を測るための指標が増えた更新です。

### ユーザーにとって良いこと
どの自動化や拡張が実際に開発者に使われているかを把握しやすくなり、投資すべきカスタマイズを見極めやすくなります。チームは利用の広がりを定量化できるため、Copilot CLI の導入効果を説明しやすくなります。

### アクションプラン
- usage metrics API の取得処理を更新し、`totals_by_skill`、`totals_by_custom_agent`、`totals_by_mcp`、`totals_by_slash_cmd`、`totals_by_plugin` を保存・可視化してください。
- `distinct_*_use_count` を定例指標に加え、利用の多様化が進んでいるか追跡してください。
- ⚠️ カスタム名は表示されないため、社内で独自に識別したい場合は別のマッピングを保持してください。

## Ubuntu 26 generally available and latest migration

**URL:** https://github.blog/changelog/2026-09-17-ubuntu-26-generally-available-and-latest-migration

### 要約
GitHub Actions の Ubuntu 26.04 runner image が一般提供になり、`ubuntu-latest` は順次 Ubuntu 26.04 に移行します。x64 と arm64 の両方で使えますが、プリインストール済みツールやバージョンの差分により、既存ワークフローが影響を受ける可能性があります。移行期間は 2026-10-19 から 2026-11-19 です。

### ユーザーにとって良いこと
最新の Ubuntu を標準で使えるようになり、ランナー環境をより新しい状態に保てます。早めに検証すれば、移行本番前に壊れるワークフローを潰しておけます。

### アクションプラン
- 重要なワークフローを `runs-on: ubuntu-26.04` で先行検証し、依存ツールや apt パッケージの差分を洗い出してください。
- すぐに移行できない workflow は `ubuntu-24.04` に明示的に pin し、`ubuntu-latest` の自動移行の影響を避けてください。
- ⚠️ `ubuntu-latest` を使っているリポジトリは、移行期間前に互換性テストを終え、必要なら修正期限を設定してください。

## Workflow execution protections in GitHub Actions generally available

**URL:** https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available

### 要約
GitHub Actions の workflow execution protections が一般提供になり、誰がどのイベントで workflow を起動できるかをより細かく制御できるようになりました。workflow ファイル単位の targeting、Insights、REST API が追加され、ポリシーをコード化しやすくなっています。public repositories では `pull_request_target` を無効化する default protection rule も導入されます。

### ユーザーにとって良いこと
危険な workflow の起動条件を絞り込みやすくなり、Actions のセキュリティを標準化できます。shadow mode で影響を見てから enforcement できるため、運用変更のリスクも抑えられます。

### アクションプラン
- 既存の Actions policy を確認し、重要な workflow はファイル単位で allowlist を作って起動条件を明確化してください。
- Insights を使って、evaluate mode でどの workflow run がブロックされるか確認し、本番 enforcement の前に影響を洗い出してください。
- ⚠️ public repository で `pull_request_target` に依存している workflow は、2026-11-02 の自動 enforcement までに代替設計へ移行するか、明示的な許可を設定してください。
